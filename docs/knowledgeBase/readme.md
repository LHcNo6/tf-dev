## 维护规则

每次完成一个功能或修复，即使改动很小，也在 `changes/` 新增一篇 Markdown，并在变更索引中链接。一次交付包含多个紧密相关的修改时，写一篇说明该次交付；互不相关的功能或修复分别记录。文件名使用有语义的小驼峰，例如 `generationWaiting20261110.md`；同名时增加小驼峰区分词，不覆盖已有记录。

每篇记录至少写明：

- 日期、功能或问题，以及这次实际改变的行为。
- 关键实现位置及相关主题文档链接；涉及原因时区分已证实结论和推测。
- 已执行的验证及结果，单独注明未验证的路径、环境和限制。
- 若有兼容性、迁移、运行或回滚注意事项，记录实际影响。

同时更新受影响的主题维护文档，使其反映当前行为；已有合适主题时直接更新，没有时新建主题文档并加入上表。主题属于子包时可维护其现有文档并从本表链接。变更记录保留当时事实，后续行为变化写新记录并更新主题，不把旧验证改写成当前验收。需求和待办继续放在 `localIssues/`，不要把计划写成已经实现的行为。不要写入密钥、私人对话或其他敏感信息。
